title: Architecture description: How maux uses a RamWorks card, in four pictures, and where the design is written down. ---

Architecture

A RamWorks card gives the enhanced IIe extra 64K banks of auxiliary memory, and one register, $C073, chooses which bank the auxiliary-memory switches see. maux gives each process one of those banks. Because ALTZP moves the zero page and the hardware stack along with it, a bank switch swaps the registers' working set, the stack and the whole address space in one motion.

Every process sees the same logical address space from $0000, so nothing is relocated and an ordinary assembler's output runs as it is. It is a poor man's MMU with 64K pages.

1. Who owns what

Main memory holds the kernel and ProDOS 8, which shares the machine. The shipped kernel is assembled at $2000 and runs up to about $97E8, so it borrows the hires pages for itself; text page 1 stays the display. The language card is ProDOS 8's (the MLI and its drivers), and the $BF00 global page is in main RAM. maux's own use of the card is bank 2: the bye resident window at $D100-$D3FF and the kernel's cold segment at $D400. The $FF00 vector page is ProDOS's too; maux patches two bytes of it, the IRQ vector.

Aux bank 0 is the kernel's annex: the process table, the per-process working directories, the pipe rings and the other per-process kernel structures. It has to be bank 0 because the video scanner reads auxiliary memory from bank 0 and nowhere else (see the 80STORE story below). Every other bank is one process.

User space is $0000-$BFFF plus $D000-$FEFF. The whole $C000-$CFFF window is carved out: it is I/O and slot ROM, always main, never process memory. The kernel's entire footprint in a process bank is the $FF00-$FFFF page the hardware already claims for vectors.

The release kernel does not probe for banks. It starts with a fixed list: banks {{fact:bank_top}} down to 2 are free for processes, and the shell is bank 1. So maux uses banks $00 to $0F and nothing else. It needs a RamWorks-compatible card with at least {{fact:min_ram_kb}} KB (a period RamWorks II or III main board fully populated gives exactly that), and it runs at most {{fact:process_max}} processes besides the kernel. The bye save banks come from the same list. A boot-time bank probe exists in the tree and is linked only into a test image. The population the gates exercise is dense; sparse and aliased cards are not verified.

2. A context switch

Both ways into the kernel, the JSR $FF00 syscall door and the interrupt door, build the same six-byte frame on the process's own stack, so one exit tail serves both. The kernel then switches ALTZP and the stack pointer to its own, does its work, writes the next process's bank number to $C073, flips ALTZP back, and returns by RTI onto the other process's stack. The one rule inside the switch is that nothing is pushed between the ALTZP flip and TXS: for that moment the stack page belongs to somebody else.

Preemption comes from a 60 Hz tick. At boot the kernel probes for an AppleMouse card and uses its vertical-blanking interrupt; failing that, it looks for a Mockingboard and runs the 6522's timer 1 free-running at about 60 Hz. With neither, no hardware source is armed and the tick counter never advances. Writes to $C073 also trip the paddle strobe, so joystick reads need the scheduler held briefly. The register is write-only and is not cleared by a reset, so the kernel never trusts what it last selected: it keeps its own copy of the current bank and writes the register before any aux access.

What this does not buy is protection. Soft switches are plain addresses, and any process can write $C073, flip RAMRD or execute SEI. Bank-per-process gives isolation for correctness, not security: a well-behaved process cannot touch another by accident, and a wild store into $C0xx can take the machine down.

3. fork, and the trap in the copy

The primary way to start a program is spawn: allocate a bank, stamp its $FFxx page, load the image, apply the file-descriptor actions. Nothing is copied from a parent. fork exists too, as the slow path for programs that need it: it clones the process's bank.

The copy is where the trap is. With 80STORE set, RAMRD and RAMWRT are ignored for $0400-$07FF and, with HIRES also set, for $2000-$3FFF; only PAGE2 routes them. A bank-copy loop that does not bracket those windows with CLR80STORE and SET80STORE reads and writes main memory instead of the aux bank, so main is copied onto itself. Nothing crashes and nothing is logged; the child simply never receives that window.

maux's first fork design was reasoned from first principles and had no bracket, and it was wrong: the IIe's documented soft-switch behaviour says exactly what 80STORE does to those windows. The design was corrected from the documentation, and the gate for fork sets both switches on purpose, because with them off it passes with the bracket deleted. Hardware claims on this site, and in the tree, are checked against the manuals and on an emulator, not against what seems plausible.

4. bye: leave maux, run ProDOS, come back

The reason is testing. The loop is: edit in vi, assemble with nas, link with ld, build with make, all under maux, and then run the result on ProDOS 8 itself, not under a shim. ProDOS's QUIT call, MLI $65, copies $D100-$D3FF from language-card bank 2 to $1000 and jumps there; every program selector works by replacing that window. bye puts a small resident there, so the QUIT the program makes to leave is the moment maux is restored.

Plain ProDOS 8 knows only aux bank 0 (through /RAM), so main memory and the annex are saved into two RamWorks banks it cannot see. For the program, /RAM is reinstalled, empty, as ProDOS makes it; on the way back it is removed again and whatever the program wrote there is discarded. The program runs on a machine that is, as far as it can tell, freshly booted. ProDOS's QUIT carries no status, so bye cannot return the program's outcome to the shell: whether it succeeded is whatever it left on the volume.

How to read them

A design document can contain dated amendments, and an old NEXT is not an assignment. When a document and the source disagree, the source and its named gate win. Hardware claims are checked against primary sources (manuals, patents, a second emulator) and graded as fact, likely or reported; only a fact is allowed to carry weight unchecked.
