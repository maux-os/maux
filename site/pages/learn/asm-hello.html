L2. hello, world, in assembly

Learn / L2

Goal: turn a 6502 source file into a program with nas and ld, run it, and then make one mistake and see how the assembler reports it.

What you need

L1 (you can edit a file with vi). The source is already on the disk, so this lesson copies it; retype it with vi if you want the practice.

The file

About twenty lines of code under a long comment. PUTS and EXIT belong to liba, maux's own small C-less library: ext says "defined somewhere else", and ld will find them.

{{file:examples/hello/hello.s}}

The session

The first half builds and runs the program. The second half, which is the film “a typo, caught”, breaks it twice.

{{gen:session}}

What just happened

nas assembled hello.s into hello.o, an object file of type $F8, the Merlin REL format. ld linked it into hello, a BIN file: the module you name goes first, at $0800, and -l a told it to pull from the library directory /usr/lib/LIBA the modules that define the names your program left open. That is why hello is much larger than the 32 bytes nas reported: the rest is liba.

A BIN file's auxiliary type is its load address, and $0800 is where every maux program starts. The shell loads hello there and runs it. The program builds its message in plain 7-bit ASCII (single quotes) ending in $0D and a zero; the console takes either polarity, and maux's own text, the kind vi writes, has the high bit set and ends lines with $8D.

A typo, caught

The first mistake changes jsr PUTS to jsr PUTZ with a vi command: :%s/jsr PUTS/jsr PUTZ/ replaces on every line. nas says:

{{sessionout:cat ERRS#1}}

That is the whole format: the label, the file, the line. Both lines came out of 2> ERRS: in Unix the shell's 2> catches the error stream, and nas prints its diagnostics there, so the screen stayed quiet and the file holds the complaint. (Its success line, with the byte count, goes to the ordinary output.) Its exit status is 1 when it fails, which is what make will use in L5 to stop. Watch the whole repair, from the failed make to vi on the line.

The second mistake is a misspelt instruction, ldq for lda. This one is reported more tersely: nas: pass 1 failed and nothing else, no line number and no reason. It is the same message you get for an instruction nas does not know, for a 65C02 instruction in a file that never says xc (the directive that enables them), and for a source file that does not exist. When you see it, look at the lines you changed last; grep -n prints a matching line with its number, which is how the session finds the line.

Try next

Change the message, assemble, link and run it again. Then make it print the message twice. The call that prints is six lines long and you already have it.
