L7. A ProDOS 8 program, built on maux, tested with bye

Learn / L7

Goal: edit in vi, assemble with nas, link with ld, drive it with make — all under maux — then run the result on a real ProDOS 8 and come back to the editor and the shell exactly where they were.

What you need

L2 (nas and ld) and L5 (a Makefile). You should also be comfortable with a hex number.

What bye does

bye suspends maux, gives the whole machine to a real ProDOS 8, and takes it back when the program that ran there quits. Main memory and the auxiliary bank are saved into RamWorks banks that ProDOS cannot see and restored afterwards; every other process stays in its own bank, untouched. The shell, the editor and everything else resume where they were.

The program you name is launched the way a program selector launches one. ProDOS's own QUIT call takes no pathname, so the selector's job, and bye's, is to store the system program's name at $280, close the open files, clear the bit map, protect the zero page, stack, text page and ProDOS global page, read the file into $2000 and jump to it. What your program finds is an ordinary freshly booted ProDOS 8: main memory, the language card and /RAM (present and empty) all its own, every open file closed, and the prefix set to the directory the file was launched from.

The limits, before you build anything

  • The file must be type SYS ($FF) and no larger than 30,720 bytes. It is loaded at $2000 and entered there.
  • A SYSTEM file loads flat from $2000, so its real size ceiling is the first thing it allocates above itself, not a number anyone chose. Put the MLI's 1 KB buffers at the bottom of free memory and every build is capped at that address. LS.SYSTEM puts them at $9800 and its other buffers above them, so it may grow to 30,720 bytes, the limit bye enforces anyway; a program is also free to put them higher still.
  • The program must QUIT. One that never quits, or reboots the machine to leave, ends the session: the saved banks survive a reset, but nothing yet restores from them, so a program that never quits costs a reboot. Save in vi before you run make test. This page describes that failure and does not stage it; the gate that produced the sessions below does not run a program that never quits.
  • QUIT carries no exit status. A ProDOS program cannot say whether it worked, so it leaves the answer in a file, and maux checks the file with ordinary tools when it is back. That is the whole idea of the lesson.

The session

The indented lines under ProDOS is running the program are the screen ProDOS drew, read by the gate while the program ran: once maux is back the console repaints and the program's screen is gone. The gate presses a key to let LS.SYSTEM quit, and then make goes on to the last recipe line, sh check, which prints nothing because cmp found no difference. Then the session breaks the test on purpose: one more line in mkwant makes WANT name a file ProDOS never listed, and make test must fail, with make: command failed and a non-zero status. A test that cannot fail is not a test; check ends with exit $st so that cmp's verdict is the script's, not rm's.

What just happened

Three things had to line up for cmp to say nothing, and each is a fact about the machine rather than about this program.

  • Names are upper case in ProDOS. The program lists what ProDOS stores, MAKEFILE; ls prints the case maux recorded, Makefile. So mkwant pipes ls through tr a-z A-Z.
  • The directory is in the order ProDOS keeps it and ls sorts. So check sorts both files before it compares them. The program has no need to sort.
  • The program writes maux's text encoding. maux writes high-bit text ending each line with $8D; a ProDOS program would normally write low ASCII and $0D. Tools such as sort hand back the encoding they were given, so a low-ASCII GOT would still differ from WANT after sorting. LS.SYSTEM writes the names with the high bit set and ends each with $8D, so the two files are the same bytes. Its screen output is the opposite case: the ROM's COUT wants the high bit set, and the program ORs it in.

That is also why the pathname in a raw MLI call is plain 7-bit ASCII in single quotes: a byte with the high bit set is not a legal pathname character to ProDOS. maux's own file names, and the text it writes, have the bit set; the MLI wants it clear. A first-time reader meets this once and should expect it.

GOT is created after the directory has been read, so it does not list itself; WANT is created by touch before ls runs, so it is in both lists. Without those two details the files would differ by one name, and the harness would be red for a reason that has nothing to do with the program.

Shipping it

The finished LS.SYSTEM is an ordinary ProDOS file. It calls only the MLI and the monitor ROM, so it needs nothing from maux, and nulib2 -a can archive it for transfer to another machine. The gate checks that claim rather than asserting it: after the lesson it copies the LS.SYSTEM that was built on maux onto a stock ProDOS 2.4 disk, with no maux on it, boots that disk on the emulator, and requires the program to list the disk's files, write its GOT and QUIT. The last lines of the session above are that run.
