L4. Shell scripting

Learn / L4

Goal: write three scripts, each with one idea: count tests its arguments, each loops and matches names, mygrep drives ed from a here-document and cleans up after itself.

What you need

L1: a script is a text file that starts with #!/bin/sh. Nothing from the assembly lessons.

maux's sh is the Bourne shell of Research Unix Version 7 with a few later conveniences, and it has no shell functions: V7 had none either. That fixes what these scripts can use.

Writing them also turned up shell behaviour that is wrong today. These are defects, reported to the release and not yet fixed; the scripts below keep clear of them, and so should yours:

  • A pipeline of more than three stages is refused with sh: syntax error. That one is a documented limit, not a defect (the manual says "at most three stages").
  • A $( ) inside an if, for or while body runs more than once, even in a branch that is not taken. A multi-line for typed at the prompt does the same. Its side effects happen every time, and a variable the body sets is still empty the first time.
  • Positional parameters ($1, $#) are not visible inside $( ). That is how this shell is built today; POSIX says they should be visible.
  • A three-stage pipeline of bare command names, such as ls | tr a-z A-Z | sort, fails inside a script file with sh: command not found printed three times. It works at the prompt, and in a script given absolute command paths, as sh < file, or read with . file.
  • When the last stage of a pipeline cannot be started, $? is 0.

The files

count: arguments and tests

$# is the number of arguments, $1 the first, [ -f ... ] tests for an ordinary file, and exit 1 ends the script with a failure status.

each: loops and case

for f in * loops over the file names the shell expands; case matches each against patterns; while read line takes lines from standard input, here a file given after done <. The $( ) on the last line runs a command and puts its output in the line.

The session

Each script is typed with cat > name and ended with ^D (control-D, end of file). cmp then compares what you typed with the copy on the disk; if it prints a line, you mistyped.

What just happened

./count with no argument took the first branch and printed the usage line; with a file that does not exist it took the last. The shell's $? holds the status of the last command, and the session prints it with echo $?: 0 means success, anything else failure. That is the entire contract between a program and a script.

each takes a directory as its operand and changes to it (cd $1) before it looks at anything; the change belongs to the script's own process, so your shell is still where you left it. It writes the listing to a file under /tmp named with $$, the shell's own process number, so two copies never share one, and reads it back with while read line ... done < file. The word 2 files on its last line came from $(ls | wc -l).

mygrep printed the same lines, in the same order, as the real grep. set -e makes the script stop at the first command that fails; trap 'rm -f $tmp; exit 1' 2 says "if signal 2 arrives (^C), delete the temporary file and stop". The last line of the session shows that nothing named mygrep was left in /tmp.
