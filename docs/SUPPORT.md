# Hardware and emulator support matrix

Status: LIVE, 2026-10-20 (serial row added, the MAME row corrected, the
release-medium boot figure re-measured). "Supported" below means the named configuration has
an automated release gate. It does not generalise to hardware that merely
resembles that configuration.

| platform / configuration | release status | evidence and boundary |
|---|---|---|
| verilogapple fast backend, enhanced Apple IIe, dense RamWorks, UltraTerm v3, AppleMouse, SmartPort | supported test rig | The canonical sweep exercises the implemented system broadly. The emulator source and binaries are pinned by `dependencies.lock.json`; operator-supplied ROM identities are checked. |
| verilogapple RTL backend | supported boot rig | `check-boot` requires both fast and RTL boot results. Most higher-level gates use fast and therefore do not independently prove RTL fidelity. |
| verilogapple SDL frontend (`make play`) | supported interactive emulator | The dependency bootstrap builds and audits `fast_sdl`. Launch requires a graphical SDL session; the headless second-host proof checks the linked executable and builds its disk image. |
| MAME `apple2ee` with RamWorks III, UltraTerm enhanced, Mockingboard or AppleMouse, and AppleIISd | independent validation rig | `make check-mame` has booted and exercised an interactive shell independently of verilogapple and found real defects. It is outside the canonical sweep (it needs MAME 0.286 on `PATH`, which the sweep hosts need not have). Its romsets are built by `make vendor-mame-roms` from the eleven ROMs in the dependency lock -- the two UltraTerm `.jed` files are among the eleven -- plus four hash-pinned downloads (docs/DEPENDENCIES.md); there is no separate ROM/JED input. It has no serial leg: nothing in `check-mame` touches the Super Serial Card. |
| Apple Super Serial Card (6551 ACIA), `/dev/ttya0`, and `tip` | supported, emulator-qualified on the verilogapple fast backend | `check-ser` (three bytes out, three bytes in through a blocked read woken by the tick-driven poll), `check-tip` (the six `tip` behaviours of docs/SERIAL.md sec 3e) and `check-tip-vim` (a host vim, TERM=vt102, driven over `tip`, screens compared with the edits applied to the file) are in the canonical sweep; `check-tip-vim` runs on hosts that have vim and prints SKIP, not a failure, on one that does not. The card model is verilogapple's `SscCard` and its modem is infinitely fast (docs/SERIAL.md sec 2), so the evidence is the driver's protocol, not any baud rate. The RTL backend has no SSC model and `check-mame` has no serial leg, so no second emulator has seen this card. **No physical Super Serial Card has been run**: the driver was written from the card manual and the Apple IIe technical reference and has never met a real 6551. The named gaps (no carrier detect, no baud control, no file transfer) are in `docs/KNOWN-LIMITATIONS.md`. |
| Enhanced Apple IIe with the original (pre-update) Videx UltraTerm | emulator-qualified; not verified on physical hardware | maux programs the card's CRTC from the 80x24 high-quality format entry in the card's own firmware, so the original card's interlaced 16-line rows and tall character set are set up the way the card's own firmware sets them up. `make check-mame` boots maux on MAME's model of this card and requires the CRTC registers R0-R11 to equal that firmware entry, a 384-line screen and the roughly 30 Hz interlaced frame rate it implies (MAME 0.286). Not tested: a real monitor holding that interlaced frame, and one open interrupt defect (`docs/CONSOLE.md` section 13): a card without Videx's 1985 field update has no `$C3FA` interrupt stub, so an interrupt taken while the card's ROM is mapped runs whatever bytes are there. maux keeps that window short, but the configuration is not claimed for real hardware until it has been measured. |
| Enhanced Apple IIe with UltraTerm v3 and dense RamWorks | not release-verified on physical hardware | The emulator configuration models this machine, but the current release evidence contains no end-to-end physical run. |
| Stock 40-column or built-in 80-column display on physical hardware | not release-verified | Emulator gates cover these terminal backends. Physical long-session evidence is still required. |
| Sparse, aliased or under-1 MB RamWorks/MultiRam-compatible population | **not supported** | The release kernel does not probe banks. `PRC_INIT` (`src/kernel/process.s`) uses a FIXED free list, banks 2-15, with the shell in bank 1: maux needs a RamWorks of at least 1 MB with all of banks 0-15 present, and runs at most 15 processes. A 512K card fails silently (no boot-time detection). A sparse map (period cards skip bank numbers) is not handled: a probed allocator exists as `src/kernel/bankprobe.s` but only `src/test/probetest.s` links it (`learning:01M5BZT24FCGW28BWFR02TAJ12`). |
| Release medium: one 32 MB / 65,535-block SmartPort volume (`full.po`) | supported on the emulated rig only | The release payload (docs/FULLDISK.md, SITE.md D2) is a BLOCK-DEVICE image at ProDOS's largest size, not a floppy image, and `make release` refuses one whose size or ProDOS volume-header block count disagrees with the builder. `check-release-image` covers determinism; `check-full` boots it (verilogapple fast backend) and reaches the shell prompt in the same 4,050,000 cycles as the 8,192-block play image (3,525,000 before the KFIX11 merge, 69265bdd, made every boot clear the annex; measured 2026-10-20), so the 16-block bitmap costs the boot nothing measurable. **MAME 0.286's emulated AppleIISd refuses the 65,535-block FILE as built** (`SD Card image size 65535 blocks of 512 bytes is not supported by SD or SDHC` / `Device Hard disk load failed: Invalid image`), but boots the same bytes padded with one zero block to 65,536 blocks (33,554,432 B -- the size the GEM CD's 32 MB volumes are shipped at, with a 65,535 in the ProDOS header) and passes `check-mame`'s `bye` phase on it, both round trips; **`make release` therefore ships the padded file** (docs/RELEASE.md), and `check-release-image` boots it in MAME and requires MAME to refuse the unpadded one [fact, MAME 0.286, a2sd, 2026-10-19; `check_mame.py --bye-only --play`]. **Which physical controllers accept a volume this size: untested, and nothing here is evidence for any of them.** What the sources say, with their grades: the AppleIISd's own README says its storage is "up to 128MB storage space (4x 65535 blocks)" [fact about the card's stated design, from its README on GitHub, 2026-10-19; never run with this disk]; the CFFA3000 is described, by a CiderPress source comment and forum posts, as exposing fixed 32 MB volumes [reported; its manual was not read]. A card whose driver executes a bare CLI mid-call (the AppleIISd firmware does) is a hazard class of its own: `learning:01M096X5CNKFNNJW8XND8BA89R`. No physical run is in the release evidence. |
| Release medium: a single 800K UniDisk 3.5 floppy | **not supported** | Stated here because the 800K era is over and the omission would otherwise read as an oversight. The system's own layout is period-authentic for two daisy-chained 800K drives and the boot path is the ordinary SmartPort block-zero contract, so a floppy-sized volume is not architecturally excluded -- but the current payload does not fit one, nothing builds or gates a split across two, and `make release` rejects an 800K image outright. Anyone wanting real floppies needs a smaller staged tree first; that is unbuilt work, not a documented configuration. |

Physical verification must record the exact Apple IIe revision, auxiliary card
and population, display card/firmware, timer source, storage controller, and ROM
identities. Passing an emulator gate must not be relabelled as a physical pass.
